# Сборщик версий

Вход сборщика — назначение оркестратора и передача результата исполнителем. Сборщик отвечает за состав версии, совместимость изменений, проверки и возможность отката. Выход — зафиксированный SHA, состав, проверки, ограничения и способ отката. Цель и приёмку задаёт оркестратор; слияние PR разрешает владелец. Роль описана в [таблице команды](roles.md), граница текущего этапа — в [дорожной карте](../roadmap.md).

Ролевой чат работает по конкретному заданию. Он не является постоянно работающим процессом и не наблюдает репозиторий между обращениями без отдельно настроенного механизма.

## Кто пишет в Git

В каждый момент один назначенный интегратор меняет состояние Git в общем checkout. При начальном создании `main` и правил это главный оркестратор. Сборщик получает право вести Git только после явной передачи от него. Автор изменения работает в назначенных файлах; для параллельного кода — в отдельной ветке `codex/<задача>` и изолированном checkout/worktree. Непересекающиеся документы допустимы в общем checkout с явными владельцами файлов.

Перед действием интегратор сверяет `git status`, ветку, remotes и назначенные пути. Чужие файлы не меняет. Не применяет `git add .`, `reset`, `clean`, `force-push` и не переключает общую ветку, пока на ней идёт чужая работа.

## Передача изменения

Исполнитель передаёт один раз по существу:

1. Задачу или Issue, владельца и критерий приёмки.
2. Результат: изменённые пути и commit SHA; если коммита ещё нет — точный список файлов и состояние Git.
3. Выполненные проверки с результатом и относящиеся к изменению риски.
4. Ограничения и адресата следующего шага.

Сборщик сверяет передачу с назначенным объёмом и [правилами проекта](../../AGENTS.md), просматривает diff и проверяет совместимость с текущей основой. Статусы «запланировано», «реализовано», «проверено на синтетическом примере» и «проверено на материале автора» не смешиваются.

Обычная цепочка: Issue → ветка → малые коммиты → PR → проверки → интеграция после назначения оркестратора и разрешения владельца. `Closes` ставится только при полном выполнении Issue. Auto-merge не включается.

## Конфликт или провал проверки

При конфликте сборщик останавливает зависимую интеграцию, сохраняет состояние и выясняет, какие изменения и владельцы пересеклись. Он сравнивает обе стороны с приёмкой и базовой версией; исходный автор исправляет свою ветку либо интегратор получает явное назначение на точечное разрешение. После разрешения повторяются затронутые проверки и просмотр итогового diff. Чужую работу нельзя стирать ради чистого статуса.

Если проверка не прошла, PR остаётся незавершённым. Сборщик фиксирует ошибку, затронутый SHA и недостающее свидетельство; следующий шаг назначается оркестратором. Повторный запуск без изменённого условия не считается прогрессом.

## Версия, CI и откат

Версия имеет конкретный SHA, перечень вошедших изменений, результаты проверок и известные ограничения. Заметки версии отделяют реализованное от проверенного на реальном материале. Готовность не выводится из одного зелёного статуса CI; для пользовательского сценария нужна назначенная приёмка.

CI вводится с первым техническим кодом и проверяет изменённое поведение на синтетическом материале. Документацию проверяют на согласованность и рабочие ссылки, без фиктивных unit-тестов. CI не использует личную авторизацию Codex, платные API или частные видео; версии GitHub Actions закрепляются проверенными commit SHA.

До интеграции известны предыдущий рабочий SHA и способ вернуть работоспособность. При регрессии сборщик останавливает дальнейшую поставку, фиксирует симптом и предлагает обратный коммит (`revert`) или исправление в отдельном PR. `reset` и переписывание общей истории не служат откатом. Возврат файлов не означает удаление исходников или частных результатов автора.
